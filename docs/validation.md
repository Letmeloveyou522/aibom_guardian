# 검증 기록

[README로 돌아가기](../README.md) · [English README](../README.en.md) · [기계 판독용 결과 요약](evidence/verification-2026-11-01.json)

이 문서는 개발 환경에서 수행한 자동 검사와 실제 연동 확인을 구분해 기록합니다.
외부 기관의 인증이나 독립적인 보안 성능 평가를 의미하지 않습니다.

## 기준과 환경

- 기록일: 2026-11-01.
- 기준 커밋: `4fec5204edddaf4e1e654615c6b1ea2b5f0f0cd7`.
- 자동 테스트 대상: 기준 커밋에 `examples/demo_scenarios.py`의 import 경로 수정과 `tests/test_demo_scenarios.py`를 적용한 작업본.
- 환경: Windows, Python 버전은 [결과 요약](evidence/verification-2026-11-01.json)의 `environment` 참고.
- 변경된 실행 코드와 관련 모듈의 SHA-256을 결과 요약에 기록합니다. 문서 수정 이후의 다른 커밋까지 이 결과가 적용되는 것은 아닙니다.

| 모니터링·Slack | 전체 테스트 중 44개 통과 | 변경 중복 방지, 조회 실패·복구, 전송 실패 후 재시도, 대기열 보존, URL 검증과 비밀 값 노출 방지 |
| pyflakes | 종료 코드 0 | `src/aibom_guardian`, `tests`, `examples`의 정적 검사 |
| README 합성 시연 | 종료 코드 0, 4개 시나리오의 자체 검증 통과 | 현재 코드에서 문서에 적힌 시연 명령의 실행 가능 여부 |

JUnit 결과에는 하위 테스트도 포함돼 총 1,066개 항목이 기록됩니다.
pytest 출력의 1,052개 테스트와 하위 테스트 14개를 별도로 집계했습니다.
모의 응답으로 동작을 검사하므로, 테스트 통과율을 실제 취약점 탐지 정확도로 해석하지 않습니다.
정적 검사나 테스트 통과는 버그가 없다는 보증도 아닙니다.

저장소 루트에서 재현할 수 있습니다. `--basetemp`는 pytest가 관리하는 임시 폴더이므로 검사 전용 경로를 사용하세요.

```bash
python -m pip install -e ".[dev]"
python -m pytest -o addopts= -q -p no:cacheprovider --basetemp artifacts/readme-final-verification-tests --junitxml artifacts/readme-final-verification.xml
python -m pyflakes src/aibom_guardian tests examples
python examples/demo_scenarios.py --compact
```

원본 JUnit 파일은 로컬 `artifacts/`에 생성됩니다. 공개 요약에는 실행 환경, 명령, 집계,
실행 시각과 JUnit SHA-256을 기록하고 로컬 경로·호스트 이름은 포함하지 않았습니다.

## 실제 연동 확인

다음은 2026-11-01 설정 과정에서 확보한 실제 실행 기록의 요약입니다.
자동 테스트의 모의 응답과 구분하며, 현재 서비스 상태를 실시간으로 보여주는 자료는 아닙니다.

| 항목 | 관측한 결과 | 해석 범위 |
|---|---|---|
| Slack 웹훅 | 테스트용 가상 변경 1건 전송, `sent_count=1`, `pending_count=0` | 실제 HTTP 전송 성공. `send_slack`은 HTTP 200과 응답 본문 `ok`를 모두 확인해야 `sent`를 반환 |
| 알림 이력과 중복 방지 | 전송 결과가 SQLite 이력과 일치, 같은 검사 재실행 시 추가 전송 없음 | 동일 변경을 반복해서 보내지 않는 정상 흐름 확인 |
| 고정 목록 재조회 | 기존 보고서의 Python 패키지 7개·모델 1개 모두 조회 성공, `complete=true` | 해당 목록과 해당 조회 시점의 성공. 배포 환경의 전체 구성요소를 발견했다는 의미는 아님 |
| 변경 없음 처리 | 변경 이벤트 0건, 알림 상태 `no_events` | 실제 목록 검사에서는 불필요한 추가 메시지를 보내지 않음 |
| Windows 작업 | 활성 상태, 마지막 작업 종료 코드 0, 매시간·로그인 트리거 확인 | 등록된 예약 작업과 첫 실행을 확인. 실제 재부팅과 장기 운영까지 검사한 것은 아님 |

웹훅 URL, Slack 워크스페이스·채널 식별자, Windows 계정 정보와 암호문은 공개 요약에 포함하지 않습니다.
다른 환경에서 실제 연동을 재현하려면 [모니터링 설정](monitoring.md)에 따라 별도 웹훅을 구성해야 합니다.

## 합성 시연의 의미

`demo_scenarios.py` 기본 모드는 합성 모델 보고서와 모의 PyPI 응답을 사용합니다.
`--live`를 주어도 모델 사례는 합성 입력이며, 패키지 사례만 실제 PyPI를 조회합니다.

| 합성 입력 | 이번 실행의 판정 | 확인한 정책 |
|---|---|---|
| 위험 신호 없는 모델 보고서 | `ALLOW`, 100점 | 근거가 충분하고 문제 없는 입력의 허용 |
| 악성 pickle 참조를 담은 모델 보고서 | `BLOCK`, 49점 | 악성 참조로 분류된 입력에 대한 강제 차단 |
| `reqeusts` 이름 유사성 | `ALLOW`, 100점 + 정보성 신호 | 이름 유사성만으로 사칭을 확정하거나 차단하지 않음 |
| 존재하지 않는 패키지 모의 응답 | `WARNING`, 93점 | 존재 여부에 대한 검토 필요 표시 |

두 번째 사례는 악성 파일을 실제 다운로드해 탐지한 실험이 아닙니다.
세 번째 사례의 `ALLOW`는 합성 입력의 정책 결과이며, 실제 패키지의 안전성을 검증한 결과가 아닙니다.

## CI와 남은 평가

[CI 워크플로](../.github/workflows/ci.yml)는 Python 3.10–3.13 테스트, 정적 검사,
패키징, 오프라인 CLI 실행을 구성합니다. 위 로컬 테스트 결과는 이 모든 환경에서의 실행 결과와 구분합니다.
워크플로의 `push` 대상은 `main`·`dev`이며, 기능 브랜치는 해당 브랜치를 대상으로 한 PR 또는
수동 실행으로 검사할 수 있습니다. 제출 커밋의 성공 여부는 [GitHub Actions 기록](https://github.com/Letmeloveyou522/aibom_guardian/actions/workflows/ci.yml)에서 확인해야 합니다.

독립된 정답 데이터셋을 이용한 탐지 정확도, 오탐·미탐률과 점수 타당성은 아직 확립하지 않았습니다.
재부팅 후 복구, 장기 가용성, 외부 장애에서의 전달 보장도 추가 검증이 필요합니다.
Slack이 수신한 뒤 응답이 유실되면 재시도로 중복 수신할 수 있어 정확히 한 번 전달을 보장하지 않습니다.
점수 정책의 평가 방법과 합성·팀 검토·외부 검토의 구분은 [방법론](trust_score_methodology.md#사례별-판정-평가)에 설명합니다.
