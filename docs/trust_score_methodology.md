# AI Trust Score Methodology
AI 공급망 신뢰성 평가 및 판정 기준
문서 경로: docs/trust_score_methodology.md
적용 대상: 소프트웨어 패키지, AI 모델 및 관련 공급망 구성요소
출력: Trust Score (0–100), Confidence (0–1), Verdict (ALLOW, WARNING, BLOCK)
설계 근거: OWASP CycloneDX 1.6, OpenChain, OWASP Top 10 for LLM and GenAI Applications
## 1. 개요 (Overview)

AI 소프트웨어는 외부 패키지, 사전 학습 모델, 모델 가중치 및 관련 구성요소에 의존한다. 이 과정에서 악성 코드, 알려진 취약점, 라이선스 제한, 타이포스쿼팅, 존재 여부가 불명확한 구성요소 및 출처 검증 실패와 같은 공급망 위험이 발생할 수 있다.

AI Trust Score는 이러한 위험을 여섯 개 카테고리로 분류하고, 카테고리별 최대 감점 한도와 심각도 계수를 사용하여 위험을 정량화한다. 최종 판정은 점수뿐 아니라 검사 증거의 충분성, 확인된 심각도 높은 문제 및 별도의 강제 차단 정책을 함께 고려한다.

본 방법론은 국제 표준과 공개 보안 가이드라인을 위험 분류 및 데이터 관리의 설계 근거로 활용한다. 다만 국제 표준이 본 프로젝트의 구체적인 가중치, 감점 공식 또는 판정 임계값을 직접 규정하는 것은 아니다. 해당 수치는 프로젝트 자체의 정책으로 정의하고 테스트를 통해 검증한다.

## 2. 표준 및 보안 가이드라인 (Standards Alignment)
### 2.1 OWASP CycloneDX 1.6: AI 구성요소의 구조화

CycloneDX는 소프트웨어 및 AI/ML 구성요소를 표현하기 위한 BOM(Bill of Materials) 규격이다. 본 프로젝트는 CycloneDX 1.6 데이터 모델을 참고하여 구성요소, 취약점, 라이선스 및 모델 메타데이터를 구조화한다.

관련 평가 항목: 취약점, 패키지·모델 존재 여부, 출처
설계 근거: 구성요소 식별 및 공급망 정보를 일관된 데이터 구조로 표현
현재 구현: CycloneDX 1.6 필드와 aibom-guardian:* 커스텀 property를 사용하여 평가 결과 및 관련 증거를 표현한다.

현재 공식 CycloneDX JSON Schema를 통한 산출물 검증은 수행하지 않는다. 따라서 본 프로젝트는 CycloneDX 1.6 데이터 모델을 참고한다고 명시하며, 공식 규격 적합성이나 완전한 호환성을 보장한다고 주장하지 않는다.

### 2.2 OpenChain: 라이선스 컴플라이언스

OpenChain의 ISO/IEC 5230은 오픈소스 라이선스 컴플라이언스 프로그램의 요구사항을, ISO/IEC 18974는 오픈소스 보안 보증 프로그램의 요구사항을 다룬다. OpenChain의 관련 가이드는 조직 차원의 라이선스 의무 및 보안 관리 체계를 설계하는 참고 자료로 활용할 수 있다.

관련 평가 항목: 라이선스, 출처
설계 근거: 구성요소 식별, 라이선스 의무 확인 및 정책 기반 검토
현재 구현: 라이선스 상태를 ALLOWED, REVIEW, UNKNOWN, NOT_INSTALLED, BLOCKED 등으로 구분하여 위험을 반영한다.

라이선스의 허용 여부는 라이선스 식별 결과와 프로젝트의 배포 정책에 따라 결정한다. 특정 라이선스의 모든 사용 형태가 일률적으로 허용 또는 금지되는 것은 아니므로, 라이선스 판정 정책은 별도로 명시해야 한다.

이러한 연결은 OpenChain의 컴플라이언스 원칙을 참고한다는 의미이며, 본 점수 공식 자체가 OpenChain의 인증을 받았다는 의미는 아니다.

### 2.3 OWASP Top 10 for LLM and GenAI Applications: 공급망 위험

OWASP Top 10 for LLM and GenAI Applications 2025의 LLM03은 공급망 위험을 다룬다. 외부 구성요소의 취약성, 모델 및 의존성의 무결성, 라이선스와 출처 관리 등은 AI 시스템의 신뢰성을 평가할 때 고려해야 할 요소다.

관련 평가 항목: 악성 코드, 취약점, 라이선스, 타이포스쿼팅, 존재 여부 및 출처
설계 근거: 외부 구성요소를 무조건 신뢰하지 않고 위험과 검증 증거를 함께 평가
현재 구현: 발견된 문제의 심각도에 따라 감점하고, 정책상 치명적인 문제는 점수와 무관하게 차단한다.

OWASP의 공급망 위험 분류는 평가 항목을 선정하는 근거다. 카테고리별 가중치와 구체적인 감점 수치는 본 프로젝트의 자체 정책으로 정의한다.

## 3. 점수 산정 방법 (Scoring Methodology)

### 3.1 카테고리별 최대 감점 한도

Trust Score는 100점에서 시작한다. 아래 배점은 개별 이슈당 고정 감점이 아니라 각 카테고리가 차감할 수 있는 최대 점수다.

| 평가 카테고리 | 최대 감점 |
| :--- | :---: |
| 악성 코드 (Malware) | 28 |
| 취약점 (Vulnerabilities) | 25 |
| 라이선스 (License) | 15 |
| 타이포스쿼팅 (Typosquatting) | 12 |
| 존재하지 않는 패키지 또는 모델 (Existence) | 10 |
| 출처 (Provenance) | 10 |
| **합계** | **100** |

카테고리 $c$에 대한 이슈별 심각도 계수를 $s_i$, 해당 카테고리의 최대 감점을 $W_c$라고 정의한다.

$$
L_c = \min \left( 1, \sum_{i \in c} s_i \right)
$$

$$
D_c = W_c \times L_c
$$

$$
S_{\text{raw}} = 100 - \sum_{c} D_c - D_{\text{unknown}}
$$

- $L_c$: 카테고리 부하. 최대 1.0이다.
- $D_c$: 해당 카테고리의 감점.
- $D_{\text{unknown}}$: 별도로 정의된 알 수 없는 이슈 유형의 감점.
- $S_{\text{raw}}$: 저장소 점수 혼합 및 최종 판정용 상한을 적용하기 전의 패키지 점수.

심각도 계수는 다음과 같다.

| 심각도 (Severity) | 계수 (Weight) |
| :--- | :---: |
| Critical | 1.0 |
| High | 0.7 |
| Unknown | 0.5 |
| Medium | 0.4 |
| Low | 0.2 |

#### 카테고리 감점 예시

| 발생 이슈 시나리오 | 산출 수식 | 최종 감점 | 비고 |
| :--- | :---: | :---: | :--- |
| **High CVE 1개** | $25 \times 0.7$ | **17.5점** | 단일 High 취약점 감점 |
| **Critical CVE 1개** | $25 \times 1.0$ | **25.0점** | 단일 Critical 취약점 감점 |
| **Critical CVE 5개** | $25 \times \min(1, 5)$ | **25.0점** | 카테고리 최대 감점 한도($W_c$) 도달 |
| **등급 미지정 타이포스쿼팅** | $12 \times 0.7$ | **8.4점** | 기본 High 계수(0.7) 적용 |

동일 카테고리에서 이슈가 증가하더라도 카테고리별 감점은 해당 배점을 초과하지 않는다. 예를 들어 Critical CVE가 여러 개 발견되면 취약점 카테고리의 감점은 최대 25점이다. 다만 별도의 Hard Block 정책은 이러한 감점 한도와 무관하게 적용될 수 있다.

### 3.2 라이선스 평가

라이선스 위험은 개별 이슈의 심각도와 license_status를 함께 고려한다. 두 정보가 모두 존재하면 더 높은 위험을 나타내는 값을 사용한다.

### 라이선스 상태별 위험 계수

| 라이선스 상태 (Status) | 위험 계수 (Weight) |
| :--- | :---: |
| ALLOWED | 0.0 |
| REVIEW | 0.3 |
| UNKNOWN | 0.4 |
| NOT_INSTALLED | 0.4 |
| BLOCKED | 1.0 |

> **산출 예시:**  
> 라이선스 상태가 `REVIEW`인 경우, 해당 카테고리의 감점은 $15 \times 0.3 = 4.5$점이다.  
> `BLOCKED`는 카테고리 최대 감점인 $15$점에 해당하며, 프로젝트 정책에서 **Hard Block** 대상으로 지정된 경우 종합 점수와 무관하게 최종 판정을 **BLOCK** 처리한다.

라이선스 정보가 미확인이라는 이유만으로 특정 라이선스 위반이 확정되었다고 간주하지 않는다. 미확인 상태는 위험 점수와 신뢰도에서 각각 정의된 규칙에 따라 처리한다.

### 3.3 알 수 없는 이슈 유형과 저장소 점수

카테고리 매핑이 없는 이슈 유형은 일반 카테고리와 별도의 감점 풀에서 처리한다.

- **알 수 없는 이슈 유형:** 이슈당 3점 감점
- **해당 감점의 최대 한도 ($D_{\text{unknown}}$):** 10점

저장소 점수가 제공되는 경우에는 패키지 점수와 저장소 점수를 다음과 같이 혼합한다.

$$
S_{\text{combined}} = 0.7 S_{\text{package}} + 0.3 S_{\text{repository}}
$$

- $S_{\text{package}}$: 개별 패키지 자체의 Trust Score
- $S_{\text{repository}}$: GitHub/오픈소스 저장소의 건전성 지표 (OpenSSF Scorecard 등 기반)

이때 저장소 이슈는 카테고리 감점에서 다시 계산하지 않는다. 이는 동일한 위험이 패키지 점수와 저장소 점수에 중복 반영되는 것을 방지하기 위한 구현 규칙이다.

최종 표시 점수는 별도의 Hard Block 표시 규칙을 적용한다. Hard Block이 발생한 경우 점수가 49점을 초과하지 않도록 제한한다. 따라서 표시 점수만으로 Hard Block의 원인을 추론해서는 안 되며, 반드시 최종 판정과 이슈 정보를 함께 확인해야 한다.

## 4. 신뢰도 산정 (Confidence)

신뢰도는 0.0에서 1.0 사이의 값으로, 기대한 검사 증거가 얼마나 확보되었는지를 나타낸다. 신뢰도는 Trust Score와 별개로 계산하며, 특정 점수 이상을 얻었다고 자동으로 높아지지 않는다.

### 4.1 기본 신뢰도

기대하는 증거 신호를 $e_j \in \{0, 1\}$, 각 신호의 가중치를 $w_j$라고 할 때 기본 신뢰도는 다음과 같다.

$$
C_{\text{base}} = \frac{\sum_{j} w_j e_j}{\sum_{j} w_j}
$$

- $e_j$: 증거 신호 충족 여부 (충족 시 1, 미충족 시 0)
- $w_j$: 개별 증거 신호의 가중치
- $C_{\text{base}}$: 기본 신뢰도 (0.0 ~ 1.0 범위의 정규화된 값)

검사 완료와 결과 미확인은 서로 다른 상태다. 예를 들어 issues=[]는 검사가 수행되어 발견 결과가 없는 상태로 취급할 수 있지만, issues=None은 검사가 수행되지 않았거나 결과를 확보하지 못한 상태다.

기본 신뢰도에 사용하는 증거 신호는 대상 유형에 따라 달라진다.

증거 신호	라이브러리	모델	저장소
유효한 라이선스 상태	1.0	1.0	1.0
이슈 검사 결과 존재 (issues is not None)	1.0	1.0	1.0
모델 정보 존재	해당 없음	1.0	해당 없음
저장소 정보 존재	0.5	해당 없음	1.0

표의 값은 증거 신호가 존재할 때 사용하는 가중치다. 각 대상의 실제 신뢰도는 적용 가능한 신호의 가중치 합을 분모로 하여 계산한다.

예를 들어 라이선스가 `ALLOWED`이고 `issues=[]`이며 선택적 저장소 정보가 없는 깨끗한 라이브러리는 다음과 같이 계산된다.

$$
C_{\text{base}} = \frac{1 + 1}{1 + 1 + 0.5} = 0.80
$$

### 4.2 신뢰도 감쇠 (Confidence Decay)

특정 검증 불확실성이 존재하면 기본 신뢰도에 감쇠 계수를 곱한다.

조건	감쇠 계수
상류 데이터의 partial_data	0.75
채점 가능한 이슈에 unknown 심각도가 존재	0.85
verified: False인 이슈가 하나 이상 존재	0.85

감쇠 조건은 해당하는 경우 곱셈으로 누적한다. 최종 신뢰도는 0과 1 사이로 제한하고 소수 둘째 자리까지 반올림한다.

예를 들어 기본 신뢰도가 $0.80$인 패키지에서 `verified: False` 이슈가 발견되면 다음과 같다.

$$
C = 0.80 \times 0.85 = 0.68
$$

이 패키지는 점수가 100점이어도 신뢰도 0.7이라는 ALLOW 조건을 충족하지 못한다.

신뢰도는 안전성의 확률이나 국제 표준 인증 점수를 의미하지 않는다. 현재 구현에서는 검사 결과 및 메타데이터 증거의 충분성을 나타내는 운영 지표로 사용한다.

## 5. 최종 판정 (Decision Thresholds)

최종 판정은 다음 우선순위 순서(Priority Order)로 평가하여 결정한다.

1. **Hard Block 발생:** 즉시 `BLOCK` 판정
2. **신뢰도 부족 ($C < 0.5$):** 점수와 무관하게 `WARNING` 판정 (근거 불충분 예외 처리)
3. **점수 미달 ($S < 50$):** `BLOCK` 판정
4. **승인 기준 충족:** 점수 $\ge 80$, 신뢰도 $\ge 0.7$, 확인된 High 심각도 이슈 없음 $\rightarrow$ `ALLOW` 판정
5. **그 외 모든 경우:** `WARNING` 판정

---

### 최종 판정 기준 요약

| 판정 (Decision) | 상세 조건 |
| :---: | :--- |
| **`BLOCK`** | - Hard Block 발생 시<br>- 신뢰도 $C \ge 0.5$인 상태에서 점수 $S < 50$점 |
| **`ALLOW`** | - 점수 $S \ge 80$점<br>- 신뢰도 $C \ge 0.7$<br>- 확인된 High 이상 심각도 이슈 부재 |
| **`WARNING`** | - 신뢰도 부족 ($C < 0.5$, 단 Hard Block 제외)<br>- 점수 또는 심각도에 따른 승인 조건 미충족<br>- 검증 미완료 및 추가 검토 필요 상태 |

---

> ⚠️ **신뢰도 예외 및 Hard Block 우선순위 정책**
>
> - **신뢰도 불충분 예외 ($C < 0.5$):**  
>   Hard Block이 발생하지 않았다면 점수가 50점 미만이더라도 먼저 `WARNING`을 반환하여, 근거 데이터가 불충분한 상태에서 섣부른 확정 차단(`BLOCK`)을 내리지 않는다.
>
> - **Hard Block 최우선 원칙:**  
>   Hard Block 정책은 신뢰도 예외보다 항상 우선한다. 확인된 악성 코드(Malware)나 정책상 차단 대상 라이선스(`BLOCKED`)는 **신뢰도 점수가 낮더라도 예외 없이 즉시 `BLOCK`** 처리한다.

## 6. 검증 상태 및 공급망 증거 (Verification & Provenance)

### 6.1 미검증과 미발견의 구분 (Absence vs Unverified)

상태 필드의 의미를 명확히 구분하여 데이터 결측으로 인한 오판을 방지한다.

| 상태 (Status Field) | 기술적 해석 (Interpretation) |
| :--- | :--- |
| `issues=[]` | 검사가 정상 완료되었으며, 해당 검사에서 탐지된 이슈가 없음 |
| `issues=None` | 검사 미실행 또는 분석 결과 미확보 상태 (검증 완료 여부 추가 확인 필요) |
| `license_unverified=true` | 라이선스 검증 미완료 상태 |
| `pii_scan_unverified=true` | PII(개인정보) 검사 미완료 상태 |

- **실패와 위반의 분리 원칙:**  
  검증 상태는 실제 구현 명세의 필드 정의에 따라 엄격하게 해석한다. 단순 네트워크 조회 실패나 타임아웃을 **존재하지 않는 패키지, 악성 코드 감염, 라이선스 위반의 확정 근거로 간주하지 않는다.**
- **안전한 기본값 처리:**  
  근거 데이터가 불충분한 경우에는 신뢰도 감쇠 및 판정 규칙에 따라 확정 차단(`BLOCK`) 대신 안전하게 `WARNING`을 반환한다.

---

### 6.2 출처와 타이포스쿼팅 (Provenance & Typosquatting)

- **타이포스쿼팅 판정 다각화:**  
  단순히 공식 패키지나 모델과 이름이 유사하다는 사실(문자열 유사도)만으로 타이포스쿼팅을 단정하지 않는다. 공식 게시자 정보, 배포 시점, 릴리스 주기, 다운로드 이력 등의 보조 메타데이터를 교차 검증하여 의심 수준을 종합적으로 평가한다.
- **공급망 출처(Provenance) 검증 증거:**  
  출처 평가는 공식 게시자(Verified Publisher), 소스코드 저장소 연계성, 아티팩트 해시(SHA-256), 디지털 서명(Sigstore 등) 및 SLSA 기반 출처 증명 등의 검증 가능한 증거를 활용한다.  
  *(단, 개별 증거가 유효하다고 해서 런타임 보안 취약점 등 모든 내재적 보안 위험이 제거된 것으로 간주하지는 않는다.)*
- **실제 미존재와 조회 실패 구분:**  
  패키지 레지스트리 장애나 일시적 통신 오류 등으로 인한 조회의 부재를 허위 구성요소(Non-existent / Hallucinated Package)로 오판하지 않도록 예외 처리를 명확히 규정한다.

## 7. 구현 일관성 및 검증 계획 (Implementation Consistency & Verification)

CLI 도구와 MCP(Model Context Protocol) 서버는 완전히 동일한 채점 코어 엔진을 공유한다. 따라서 동일한 입력 데이터와 동일한 정책 설정에 대해서는 인터페이스와 무관하게 완전히 일관된 점수와 판정 결과를 반환해야 한다.

### 7.1 핵심 검증 체크리스트 (Verification Checklist)

구현 검증 시 다음 항목의 정합성을 필수로 점검한다.

- [ ] **가중치 동기화:** 카테고리별 최대 감점 한도($W_c$)와 심각도 계수($s_i$)가 실제 코드 구현과 일치하는가?
- [ ] **라이선스 위험 반영:** 라이선스 자체 상태와 개별 라이선스 이슈 중 더 높은 위험 계수를 정확히 반영하는가?
- [ ] **미지정 이슈 중복 방지:** 알 수 없는 이슈 유형($D_{\text{unknown}}$)에 대한 별도 감점이 중복 적용되지 않는가?
- [ ] **저장소 점수 혼합:** $S_{\text{combined}}$ 산출 시 이미 반영된 저장소 지표가 패키지 감점 풀에서 이중 감점되지 않는가?
- [ ] **Hard Block 상한 준수:** Hard Block 발생 시 최종 표시 점수가 49점을 초과하지 않도록 상한(Cap)이 적용되는가?
- [ ] **판정 우선순위 준수:** 신뢰도 감쇠 로직 및 의사결정 트리의 판정 순서가 설계 명세와 일치하는가?
- [ ] **결측값 분리:** 미검증(`unverified`) 상태와 정상 검사 완료 후 미발견(`issues=[]`) 상태를 엄격히 구분하는가?
- [ ] **엔진 동등성:** CLI와 MCP 환경에서 동일한 패키지 입력에 대해 완전히 일치하는 결과 스키마를 반환하는가?

> 📌 **규격 적합성 관리 참고사항**  
> 현재 버전의 CycloneDX 산출물은 핵심 필드 매핑 및 기본 메타데이터 수준의 단위 테스트를 수행하며, 공식 JSON Schema 검증은 수행하지 않는다. 규격 엄격성 검증은 향후 릴리스 로드맵을 통해 별도 작업으로 통합 관리한다.

## 8. 결론 (Conclusion)

AI Trust Score는 OWASP, CycloneDX ML-BOM, OpenChain 등의 공급망 표준과 AI 보안 가이드라인을 기반으로 머신러닝 및 오픈소스 구성요소의 위험을 정량화하고, 프로젝트 정책에 따른 배포 자동화 의사결정을 지원하는 체계다.

### 본 방법론의 핵심 설계 요약

1. **정량적 위험 모델링:** 카테고리별 최대 감점 한도($W_c$)와 심각도 계수($s_i$)를 정의하여 특정 취약점의 왜곡된 과다 감점을 방지한다.
2. **신뢰도($C$) 분리 평가:** 검증 증거의 충족도를 별도로 산출하여, 데이터 결측 상태에서의 섣부른 확정 차단(`BLOCK`) 또는 오승인(`ALLOW`)을 방지한다.
3. **Hard Block 최우선 원칙:** 신뢰도나 합산 점수와 무관하게, 확인된 치명적 위험(Malware, 금지 라이선스)은 즉시 차단한다.
4. **표준과 커스텀 정책의 분리:** 국제 표준의 구조적 설계 원칙을 준수하되, 실제 조직 및 파이프라인의 요구에 맞춰 점수 가중치와 임계값을 유연하게 구성할 수 있다.

향후에는 공식 CycloneDX JSON Schema 검증을 CI/CD 파이프라인에 직접 통합하고, 실제 오픈소스 AI 파이프라인 데이터셋을 기반으로 탐지 정확도와 판정 재현성을 지속적으로 고도화할 계획이다.
